# SYSTEM INDEX — источники истины симуляции

Этот файл не заменяет память, дневник, рекорды или характер НОВЫ. Он задает
порядок чтения и записи, чтобы агент не путал слои RPG-системы и не ломал
накопленную историю.

---

## Инварианты

1. Существующие записи памяти, дневника, рекордов, worldview и личности не
   переписываются ради "красоты". Для исправления факта добавляется новая
   запись с датой и причиной.
2. Статус, XP, streak, рекорды и квесты не объявляются выполненными без
   записи в соответствующий журнал.
3. Один факт имеет один основной источник истины. Остальные файлы могут
   ссылаться на него, но не должны расходиться с ним.
4. Любая большая правка начинается с чтения этого файла, `AGENT_OPERATIONS.md`
   и конкретного файла-владельца данных.
5. Симуляция усиливает реальную жизнь: план, лог, обратная связь, проверка.
   Ролевая форма не отменяет медицинские, юридические, финансовые и
   технические ограничения реального мира.

## Потоки обновления

### Ежедневный цикл

1. Утро: прочитать `planner.md`, `quests.md`, `stats.md`.
2. Выбрать главную цель дня, до 5 действий и минимум 3+1.
3. В течение дня: новые факты писать в профильные файлы, не в общий хаос.
4. Вечер: обновить `diary.md`, `logbook.md`, затем при необходимости
   синхронизировать `stats.md`, `quests.md`, `skill-log.md`.

### Недельный цикл

1. Прочитать `logbook.md`, `planner.md`, `goals.md`, `battle-log.md`.
2. Свести XP, streak, провалы, лучший день, главную проблему.
3. Перенести незакрытые задачи в backlog или удалить как мусор.
4. Обновить недельные цели и 1-3 системные контрмеры.

### Работа с памятью

Если пользователь говорит "запомни", "память", "сохрани":

1. Определить тип памяти: личный факт, мировоззрение, процесс, квест, запись дня.
2. Записать в файл-владелец из матрицы.
3. Для Telegram/API durable memory использовать gateway-протокол `[MEMORY ...]`,
   если он доступен в текущем prompt. Это отдельный слой от markdown-файлов.
4. Если доступен Hindsight, сохранить туда компактную дополнительную запись с
   тегами. Hindsight — долговременный recall, не замена проверенной записи в
   файле-владельце.
5. OpenRAG использовать для документов и retrieval/ingestion, а не как
   ежедневный журнал.
6. Ответить только после успешной записи или честно указать сбой.

### Новая задача или проект

1. Создать запись в `quests.md` или профильной папке проекта.
2. Добавить критерий завершения.
3. Если задача большая — добавить план в `planner.md`.
4. После выполнения — запись в `logbook.md` и при необходимости XP/skill-log.

## Проверка консистентности

Перед ответом "готово" по RPG/life-задаче агент проверяет:

- [ ] Прочитан файл-владелец данных.
- [ ] Новая информация записана append-only или явно как новая версия.
- [ ] Если изменены XP/streak/статы — есть основание в дневнике/логе.
- [ ] Если создан квест — есть тип, награда, критерий завершения.
- [ ] Если создана привычка — есть место ежедневной проверки.
- [ ] Если была ошибка агента — есть запись в `nova/reflection-log.md` или
      pattern register, если это повторяющийся класс.
- [ ] Ответ пользователю не заявляет того, что не было записано.

## Минимальный контекст для агента

Для любой задачи про симуляцию:

1. `SYSTEM_INDEX.md`
2. `AGENT_OPERATIONS.md`
3. `README.md`
4. Конкретный файл-владелец из матрицы
5. Последние релевантные записи `diary.md` / `logbook.md` / `battle-log.md`

Если задача не про симуляцию, эти файлы не надо читать автоматически.
